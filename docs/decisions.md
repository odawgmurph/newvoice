# NewVoice — Decisions Log

Stage 0 decisions (Nov 17, 2026). Add new entries at the bottom. To change a decision, add an entry that supersedes it rather than editing the old one.

## D1 · App framework: React Native (Expo, development build)

- `app/` is an Expo app (SDK 58, TypeScript) using a custom development build. Expo Go is not supported, because the app needs a native audio module.
- Audio goes mic → Swift/Kotlin module → Rust on a native thread. Only computed results (about 100/s) reach JavaScript.
- Native bindings use **UniFFI** (`core/newvoice-ffi`), which generates the Swift and Kotlin bindings.
- `ios/` and `android/` are generated by Expo; they are not committed or edited by hand. Native behaviour is set through config plugins.

## D2 · No external advisors for now

The build plan's advisor gates (Stage 3 view review, Stage 5 SLP sign-off, Stage 7 stereotype review, Stage 8 clinical review) have no reviewer. What replaces them:

- **Safety limits are fixed in code and covered by tests, not configurable.** They are the handbook's limits at their conservative ends: required SOVT warm-up and cool-down, a ~20-minute soft session cap plus a daily maximum, a hard stop on pain, rawness, hoarseness or rising effort, never rewarding F0 above the user's comfortable p90, and ENT + SLP referral copy.
- **Neutral labels by default** (lighter/heavier, brighter/darker). Gendered bands only appear if the user opts in.
- **Recommended, not yet decided:** one paid SLP review of the exercises and safety rules before public launch (Stage 8).

## D3 · Positioned as an education app

- NewVoice is general wellness/education. Copy never says therapy, treatment, diagnosis, clinical or dysphonia, and never claims how the user's voice will be perceived.
- Open questions for counsel before launch: biometric-data law (BIPA "voiceprint", TX, WA), Washington's My Health My Data Act (which covers gender-affirming care information), and GDPR Art. 9. Processing on the device with no account is expected to reduce exposure, but that still needs confirming.

## D4 · Licence: Apache-2.0, plus the Margarita Clause

- All code is **Apache-2.0** (`LICENSE`). Reasons: it allows a later closed or commercial version, it is compatible with the App Store, and it includes a patent grant.
- `NOTICE` carries the **Margarita Clause**, a Beerware-style request to buy odawgmurph a margarita. Apache-2.0 §4(d) makes every redistribution carry `NOTICE`, so the request travels with the code. The clause is explicitly non-binding.
  - A binding version would make the licence non-OSI and not identifiable as standard Apache-2.0 by SPDX, which would get the project flagged by licence scanners.
- The name and icon are protected by `TRADEMARKS.md`: forks must rename. This is how the project stops a fork that removes safety limits from passing as NewVoice.
- `content/` (curriculum text) is under Apache-2.0 for now. **Revisit before Stage 5 content authoring.** CC BY-SA 4.0 is the recommended alternative if the curriculum should be reusable as content.

## D6 · Reference norms come from raw data

- `harness/norms/build_norms.py` downloads Hillenbrand (1995) `vowdata.dat` from a mirror pinned by commit and SHA-256. It writes `content/norms/reference_norms.json`, which is versioned by `schema_version` and `generator_version`.
- Only the derived statistics are committed. The raw data is not redistributed.
- Each group (adult men and women) has per-vowel F0–F4 statistics (in Hz and natural-log Hz), the F1×F2 covariance for vowel-chart ellipses, per-speaker F0, ΔF and aVTL.
- CI regenerates the file and fails if it differs from the committed version. Any change to how scores are computed must bump the version.

## D8 · Analysis core design (Stage 1)

Choices made while building `newvoice-core`. The evidence for each is in [`validation/stage1-synthetic.md`](validation/stage1-synthetic.md).

- **No runtime dependencies.** The core is plain Rust (DSP, LPC, root finding and resampling written in-crate), so the licence review stays trivial and the same code builds for iOS, Android and WebAssembly.
- **Fixed internal rates.** Pitch runs at 16 kHz and formants at 2 × the ceiling, as in Praat. Input at any capture rate is resampled by windowed-sinc interpolation onto a fixed output grid, and the grid samples are cached so overlapping frames share work.
- **One frame grid for batch and live.** Frame *k* is centred at *k* × 10 ms. `StreamAnalyser` and `analyse` run the same per-frame code on the same samples, and a test checks that they produce identical frames for any chunk size.
- **Live latency.** Frames are emitted 50 ms after their window closes (about 78 ms after their centre), so the octave-jump guard can confirm a 50 ms run before showing it. Analysis cost is about 4% of the 10 ms hop on x86. The Stage 2 ARM measurement uses `newvoice-cli bench`.
- **Pitch.** YIN is the default and MPM the alternative; both are within 1% of Praat on the corpus. YIN compares a span centred in the frame for every lag, because the textbook form skews glides by about 0.6%. Semitones use the MIDI scale (A4 = 69), so a reading is also a note number.
- **Formants.** These follow Praat's Burg method exactly, plus one deliberate difference: poles wider than 1000 Hz are dropped before numbering F1, F2 and so on. Those poles model spectral tilt rather than resonances, and in Praat's raw output they often take the F2 slot. The harness compares against Praat with the same filter (worst difference ≤ 1.1%). **Revisit the 1000 Hz value once real recordings are in the corpus.**
- **Ceiling sweep.** For sustained vowels, 4500–6500 Hz in 250 Hz steps. The score is Fast Track's track smoothness plus how much F1–F3 move when the ceiling steps to its neighbours, both in Hz. Smoothness alone cannot choose between ceilings on a steady vowel. The ceiling chosen on the baseline vowels becomes the user's live ceiling.
- **Formant confidence is provisional.** A hand-set function of F0 and the F1/F2 bandwidths, until it can be fitted to measured error.

## D9 · Validation tooling

- `core/newvoice-cli` runs the core on WAV files and prints JSON. It is test tooling and is never shipped, so it may use crates (hound, serde_json) that the core does not.
- The harness uses Parselmouth (GPL), NumPy and SciPy as **dev** dependencies only (D5).

- `uv run python -m validation.report` regenerates `docs/validation/stage1-synthetic.md`. Rerun it, and commit the result, with any change to the analysis.

Before this, a push to a branch with an open PR started two identical runs, one for `push` and one for `pull_request`, and the concurrency group could not cancel either because their refs differ.

## D10 · Voice-quality measures (Stage 1)

Evidence for each choice is in [`validation/stage1-synthetic.md`](validation/stage1-synthetic.md), under "Voice quality" and "Octave traps".

- **Live per-frame measures.** Every voiced frame carries H1–H2, H1*–H2*, alpha ratio, Hammarberg index and L/H ratio, computed on the 16 kHz pitch frame. This adds about 0.15 ms per frame. The band edges are part of each measure's definition (alpha 50 Hz–1 kHz against 1–5 kHz; Hammarberg 0–2 kHz against 2–5 kHz; L/H 50 Hz–4 kHz against 4–8 kHz). Changing a band edge, or any other definition, bumps `QUALITY_VERSION`, because stored baselines are only comparable within one version.
- **Harmonic amplitudes** come from maximising the windowed DTFT near k·F0, not from FFT bins.
- **H1*–H2*** uses the Iseli–Alwan correction with Hawks & Miller formula bandwidths, as VoiceSauce does. LPC bandwidths are not used because they are unreliable at high F0. The correction is accurate away from F1 but can be several dB off when H1 or H2 sits on F1. Within one vowel, uncorrected H1–H2 changes exactly with the source. Users are therefore only ever compared with their own baseline on the same vowel.
- **CPPS and HNR replicate Praat**, so values compare with the literature: CPPS follows Praat 6.1's `To PowerCepstrogram` + `Get CPPS` with default settings, and HNR follows `To Harmonicity (ac)`, the Gaussian-window variant. Both are batch measures for finished utterances.
- **Jitter and shimmer** use a cleaner cycle tracker than Praat's point process (cross-correlation between consecutive cycles, guided by the F0 track, bridging voicing gaps of up to 30 ms). Praat's validity rules and its amplitude definition (Hann-windowed RMS over ±0.2 periods) are kept. The results agree with Praat to within 10–15%.
- **Weight index (heuristic, `WEIGHT_INDEX_VERSION` 1).** The mean of three z-scores against the user's baseline: −(H1*–H2*), alpha ratio and CPPS. The SDs are floored at 1.5 dB, 1 dB and 0.75 dB respectively. Live frames have no CPPS, so a live index uses the other two. It must be presented as a proxy until the Stage 10 listener study.
- **Pitch octave guard (supersedes D8's "first good candidate" behaviour).** With a weak fundamental and H2 on F1, both YIN and MPM read an octave high, while Praat did not. Now, when the double period's normalised square difference (sub-sample, NSDF) leaves under a quarter of the chosen lag's aperiodicity, the estimator switches to the double period. That only happens when the chosen lag is clearly imperfect (aperiodicity above 0.02). A Praat-style global octave cost was tried first and rejected: on jittery voices it caused sub-harmonic errors, 27% of frames at 300 Hz with 1% jitter. Golden tests now cover both traps.
- **Still YIN by default.** MPM degrades less than YIN on strongly jittered voices (beyond about 2%). Revisit the default with real recordings.

## D11 · Completing Stage 1: pYIN, resonance score, real recordings

Evidence for each choice is in [`validation/stage1-real.md`](validation/stage1-real.md) and [`validation/stage1-synthetic.md`](validation/stage1-synthetic.md).

- **pYIN for finished recordings.** `PitchAlgorithm::Pyin` implements Mauch & Dixon (2014) with librosa's defaults: 100 thresholds under a beta(2, 18) prior, 0.1-semitone bins, at most 35.92 octaves/s, 1% voicing switch probability. It differs from librosa in two ways: each candidate goes through the same octave guard as YIN, and a voiced frame reports its candidate's interpolated F0 rather than the bin centre. It needs the whole utterance, so `StreamAnalyser` and the FFI's `LiveAnalyser` refuse it. `default_recording_settings()` uses it, while `default_settings()` (live) stays on YIN. On the Hillenbrand vowels pYIN makes the fewest gross F0 errors (0.4%), and on LibriSpeech it finds the most voiced frames.
- **YIN stays the live default (settles D10's open question).** On real speech YIN beats MPM on within-1% agreement with Praat and on gross errors in every condition, including the telephone channel. MPM's voicing recall is only 1–2 points higher. MPM's other advantage only appears on synthetic voices with more than 2% jitter.
- **The median filter only replaces outliers (supersedes D8's 5-frame median).** A frame is replaced by the 5-frame median only when it is more than 1 semitone from that median. On LibriSpeech the plain median cut YIN's within-1% agreement with Praat from 93% to 83%, because it clipped intonation peaks and was biased at voicing edges. The outlier rule keeps the 93% with the same gross-error rate, and still removes blips (`SmoothConfig::median_outlier_st`). The handbook's "median filter (5–7 frames)" exists as an octave-error guard, and this keeps that role.
- **The octave guard checks every multiple of the period (supersedes D10's double-period guard).** On men's /ɝ ʊ ɪ/ in the Hillenbrand set, H4 sits on F1 and is 12–29 dB stronger than H1–H3, so YIN and MPM read 3–4× the F0. The synthetic traps only had a dominant H2. The guard now tries k = 2, 3, … and takes the first multiple that passes the same NSDF ratio rule, never the best one, so a sub-harmonic can't win. YIN's gross errors on those vowels fell from 4.1% to 1.7%.
- **Resonance score (`RESONANCE_SCORE_VERSION` 1, a heuristic).** This is handbook §3.3's formula: z = ln(F/F_men) / ln(F_women/F_men) per vowel and formant, against the Hillenbrand groups' geometric means, then a weighted median over formants and tokens. F2 has weight 2, F1 and F3 weight 1, each times the token's confidence. A vowel's formant is skipped when the groups' separation is under d′ = 1, which drops F1 of /o/ and F2 of /ʊ/ and /u/; this is how "F1 where vowel-appropriate" is applied. The app labels it brighter/darker, never by gender (D2).
  - On real speakers scored over their 12 vowels, it agrees with the score from hand-checked formants to a median of 0.06–0.07. A single token is much noisier (median error 0.15), so exercises must score several vowels.
  - `delta_f_position()` puts ΔF on the same scale as a separate readout. It is not mixed into the score.
- **The core reads norms from a generated Rust table.** `harness/norms/build_norms.py` writes `core/newvoice-core/src/reference_norms.rs` from the same statistics as the JSON, so the core stays dependency-free. CI fails if either output is stale, and a harness test checks the Rust formula against an independent Python implementation.
- **Known vowel boundaries.** `measure_vowel_between()` measures the middle half of a given segment, which is the build plan's "steady-state vowel midpoints when boundaries are known". Prompted vowels and, later, aligned ones use it.
- **The 1000 Hz bandwidth filter stays (settles D8's open question).** On the Hillenbrand vowels any cutoff from 600 to 1500 Hz does about equally well. Without a filter, women's F2 and F3 lose 2–3 points within 10%.
- **Formant confidence is fitted, not hand-set (supersedes D8's provisional heuristic).** It is (1 − P(error)) × an F0 term. P(error) is the probability that F1 or F2 is off by more than 10%, fitted as a logistic curve in the wider F1/F2 bandwidth on the Hillenbrand vowels at their steady state: P = 1/(1 + exp(4.56 − 0.898·B/100)). The F0 term is 1 up to 250 Hz, falling to 0.3 at 400 Hz; real adult voices showed little F0 effect, and the drop comes from the synthetic error curve. It ranks real errors with AUC ≈ 0.8, where the old heuristic managed 0.57–0.66. The real data only go up to about 300 Hz.
- **Real recordings in the harness.**
  - *LibriSpeech:* 20 dev-clean utterances (10 men, 10 women) are committed in `harness/corpus/librispeech/`. They are CC BY 4.0, credited in `NOTICE`, and the selection is reproducible from the SHA-pinned tarball. They are tested clean, with white noise at 20 and 10 dB SNR, and through an emulated telephone channel (300–3400 Hz, 8 kHz, μ-law), with Praat on the clean audio as the reference.
  - *Hillenbrand:* the recordings are downloaded from Santiago Barreda's GitHub mirror, which hosts them with Hillenbrand's permission. They are pinned by commit and SHA-256, cached in CI and **not committed**, since no licence for the recordings is stated.
  - *VCTK:* not used. It is an 11 GB download, and the two sets above cover read speech and hand-checked vowels.
  - Hillenbrand's original site (homepages.wmich.edu) no longer resolves.
- **WASM is checked to compute what native computes.** The harness builds `newvoice-cli` for `wasm32-wasip1`, runs it under Node's WASI, and requires output equal to native to within 1e-9 relative. dB values get 0.001 dB, because HNR near 100 dB magnifies last-place rounding. So the Praat golden results hold for the WebAssembly build.
- **ARM timing moves to Stage 2.** Per-frame cost on a low-end phone needs the device matrix. x86 cost is in the synthetic report, and `newvoice-cli bench` is the tool to use.

## D12 · iOS capture spike and test distribution (Stage 2)

- **Capture.** `AVAudioSession` uses category `.record` and mode `.measurement`, which asks for the least processed input iOS offers: no voice processing, AGC or EQ. It prefers 48 kHz and a 5 ms I/O buffer. Audio arrives through an `AVAudioSinkNode`, which delivers buffers at the I/O size, unlike an input tap, which can batch about 100 ms. The realtime callback only copies channel 0 into a fixed ring buffer and does no allocation.
  - The ring uses a short `os_unfair_lock`. That is acceptable for the spike. If the device matrix shows glitches, the follow-up is a lock-free ring.
- **Analysis thread.** Every 5 ms a serial `userInteractive` queue drains the ring into the Rust `LiveAnalyser` (UniFFI), pulls finished frames, and sends batches to JavaScript about every 16 ms with `sendEvent`, which schedules onto the JS runtime. Raw audio never reaches JavaScript (D1).
- **Capability report.** `getCaptureInfo()` and the `onCaptureInfo` event report what iOS actually granted: whether the session is in measurement mode, the iOS microphone mode (Voice Isolation and similar), the input route with Bluetooth flagged, the sample rate, the I/O buffer and input latency. Each frame batch carries the analysis lag and input latency, so the app can estimate mic-to-screen latency.
- **Packaging the Rust core.** `core/scripts/build-ios-xcframework.sh` builds `NewVoiceFFI.xcframework`, which contains the static library only, and generates the Swift API with `core/uniffi-bindgen`. The C header is compiled as part of the `NewVoiceAudio` pod, so the generated Swift reaches it through the pod's own module and the C declarations exist once. The generated files live in `app/modules/newvoice-audio/ios/rust/` and are not committed.
- **Drawing.** The trace uses `@shopify/react-native-skia` 2.14 and Reanimated 4.7, with `react-native-worklets`. These are the SDK 58 bundled versions; `npx expo install` couldn't reach Expo's version API from the build sandbox, so they were installed at those exact versions. The path is built on the UI thread from a shared value.
- **Test distribution without a paid Apple account or a Mac.** The `ios-app.yml` workflow builds an unsigned Release `NewVoice.ipa` on GitHub's macOS runners, which are free while the repository is public. Testers sign and install it with AltStore and a free Apple ID, which expires every 7 days; see `docs/install-iphone.md`.
  - This covers the owner's own iPhone. It doesn't scale to the Stage 2 device matrix's iPhones or to the Stage 8 beta: those need TestFlight, and so the paid Apple Developer Program, or testers who sideload themselves. **Settled by D14:** testers sideload themselves; no paid account for now.
- **Bundle identifier** is `app.newvoice.spike` for now. The discreet app name and icon are Stage 4 work.

## D13 · Diagnostics export for the device matrix (Stage 2)

- **Test clip.** *Record test clip* starts a capture that also keeps, in memory, every sample the live analyser receives from capture start, the frames it produced, and the time spent in the analyser. It stops by itself after 30 s. Because the clip starts with the capture, frame k of the phone and frame k of any analysis of the WAV are at the same time, with no alignment step.
- **Export.** *Export diagnostics* writes `nv-<model>-<input>-<time>.wav` (mono 32-bit float, the layout of the harness's `synth.write_wav`) and a `.json` report, then opens the iOS share sheet. The report holds the device model and OS, the analysis settings, capture info at the start and end of the clip, the live frames as columns, the live analysis cost, a benchmark, and JavaScript's timing series (mic-to-screen, bridge, frame rates) as median/p95/max. The layout is versioned (`formatVersion` 1), and the harness refuses other versions.
- **ARM cost is measured on the phone, from the clip.** After capture, the clip goes through a fresh `LiveAnalyser` in 5 ms chunks as fast as it can, best of 3: the same measurement as `newvoice-cli bench`, through the FFI. The budget is 25% of the hop, the share CI already holds x86 to (`tests/test_realtime.py`).
- **Scoring (`harness/validation/device.py`).** Each clip gets three checks: the desktop core reproduces the phone's frames (streaming equals batch, so any difference is the phone build, the FFI or dropped samples); the live F0 and F1/F2 against Praat on the same audio, using the handbook's golden-comparison method ("Testing DSP": F0 ±1%, F1/F2 ±5–8%); and the Stage 2 budget. Rows go in `docs/validation/device-matrix.md`. `tests/test_device.py` checks the scorer on a synthetic export.
- **Privacy.** This is the only path where audio is written to disk, and it only runs when the user taps *Record test clip*. The clip stays in memory until exported, the export lives in the app's temporary folder, each export deletes the one before, and nothing leaves the phone unless the user picks a destination in the share sheet. Clips are not committed to the repo; only scored rows are.
  - **Pending decision:** before the Stage 8 beta, this has to move behind a developer setting or out of release builds, since the handbook's privacy model is audio processed on the device by default (Stage 4 privacy work).
- **Not compiled here.** The Swift was written without a Mac. The `ios-app.yml` workflow compiles it, and the first real export is its end-to-end test.
- **First export (Nov 21, owner's iPhone, built-in mic).** It worked end to end, and showed two bugs, now fixed: missing values were written as the string `"<null>"` instead of `null` (`jsonSafe` turned `NSNull` into its description), and the start-of-clip capture info reported the previous clip's length. `device.py` reads files from the buggy build, and scores the budget from the JSON alone when the WAV isn't next to it.
- **Settled by D16 (4 frames). Was pending: live look-ahead.** Mic→screen came in at 104 ms median (108 p95) against the handbook's ~100 ms. 80 ms of it is analysis lag: `Config::lookahead_frames` = 5 (50 ms) plus ~30 ms of window. Options:
  - *Keep 5 frames* and accept ~105 ms. The jump guard keeps confirming 50 ms runs before a pitch jump is drawn.
  - *Cut to 2 frames* (the median filter's radius, its minimum): about 30 ms less, so ~75 ms. Where the jump guard needed more look-ahead, a streamed frame can then differ from the batch frame, so the trace may briefly show an octave jump that the stored recording won't.
  - Recommended: 2 frames for the live trace only, after checking on LibriSpeech how often the streamed and batch tracks then differ; recordings keep full look-ahead because they go through batch analysis.

## D14 · Stage 2 device testing is the owner's iPhone only (supersedes the device matrix)

- **The 15–25 phone device matrix is dropped.** The owner's iPhone is the only device the project tests on. Stage 2's exit criteria (latency, frame rate, accuracy against a Praat reference, the low-end ARM timing) and the go/no-go are judged on that one phone.

The capability report (D12) is the main defence: it shows what the OS actually granted, so a tester can see why readings look off. Revisit before the Stage 8 beta, which still assumes TestFlight and Play internal testing.

## D15 · App shell, encrypted storage and the privacy layer (Stage 4, first iteration)

- **Navigation** is Expo Router, with routes in `app/src/app/`. The Stage 2 spike stays in `app/App.tsx` and is mounted as the `/capture` route, so ongoing capture work there merges cleanly. The route wrapper stops the microphone when the screen unmounts; leaving it, quick exit and the lock all unmount it.
- **Storage** is `expo-sqlite` with SQLCipher (config plugin `useSQLCipher`) and Drizzle. The tables follow the handbook's data model (§4.5): `user`, `session`, `recording`, `skill_state`, `journal`. Migrations are generated by `drizzle-kit` into `app/drizzle/`, committed, and run at start-up. Timestamps are set in JavaScript rather than with SQL defaults, so the schema doesn't depend on the SQLite version SQLCipher bundles.
- **The database key is random, not derived from the PIN.** It is 32 random bytes in the Keychain/Keystore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), applied as a raw SQLCipher key. A PIN-derived key would turn a forgotten PIN into lost data and still need a stored copy for Face ID. The PIN gates the app; the Keychain protects the key.
  - **Fail closed.** If the build has no SQLCipher, `PRAGMA key` would be silently ignored and data stored in the clear. The app checks `PRAGMA cipher_version` and refuses to open the database instead.
  - **A database the key can't open** (for example restored from a backup onto another phone, since the key never leaves the device) shows a screen offering to start fresh. The data can't be recovered.
  - **Fresh installs clear old Keychain items.** iOS keeps Keychain items after an app is deleted. A marker file in Documents, which is deleted with the app, tells a fresh install apart, so a reinstall doesn't inherit an old PIN or key.
- **PIN lock.** 4–8 digits, stored as a salted SHA-256 in the Keychain. No hash makes a short PIN resist offline guessing, so the protection is the Keychain itself plus a retry wait: five free attempts, then 30 s doubling to a cap of an hour, counted across restarts. There is deliberately **no wipe after N failures**, so someone else guessing can't destroy the user's data. Optional Face ID/Touch ID unlock uses biometrics only; the app PIN, not the phone passcode, is the fallback. The app locks whenever it goes to the background.
- **Quick exit** is an Exit button in the header of every screen. It replaces the app with a blank black screen and locks it; everything behind is unmounted. A 1.5 s press on the blank screen brings the app back, through the PIN if one is set. An app can't close itself on iOS, so this is the closest equivalent. While the app is inactive, a blank shield covers it so the app-switcher snapshot shows nothing.
- **Delete all data** closes and deletes the database and its key, the recordings folder and the PIN, then restarts at onboarding.
- **Playback is opt-in and metrics-only is the default** (handbook §2.7): onboarding offers numbers only (default), keep audio without playback, or keep audio and listen back.
- **Hormone/surgery and SLP questions are optional**, default to "prefer not to say", and are stored only as fixed choices.
- **Look: the NewVoice design system** from the "NewVoice — Sample UI" design canvas (tokens version 1). `app/src/ui/theme.ts` carries its colour tokens for light and dark (following the phone's setting, so `userInterfaceStyle` is now `automatic`), type scale, spacing and radii; `app/src/ui/kit.tsx` carries its components (primary button with the press ledge, secondary, quiet, choice cards, the pill Exit button, step dots, raised cards). Change a token in the design first, then in `theme.ts`.
  - **Fonts are bundled, not fetched:** Fraunces 600 for display, Atkinson Hyperlegible 400/700 for text, DM Mono 500 for readouts, from the `@expo-google-fonts` packages (OFL-1.1; listed in `NOTICE`). Only those four files ship.
  - **Onboarding follows the Onboarding board:** back · step dots · Exit header, display heading, radio cards with hints, action pinned to the bottom. Home keeps a placeholder until lessons exist; the board's path, today card and tab bar come with Stages 5–6. The capture spike keeps its own dark look.
  - **"stop" is used for errors and the delete-all button.** The design reserves it for hard stops; a destructive, irreversible action is the closest app-shell equivalent. Revisit if the design adds a separate destructive token.
- **Unit tests** for pure app logic run under Node's built-in test runner (`npm test`), so no test framework is needed yet; CI runs them.

## D16 · Live look-ahead is 4 frames (settles D13's pending decision)

Evidence: [`validation/live-lookahead.md`](validation/live-lookahead.md), generated by `harness/validation/lookahead.py`, which streams the 20 LibriSpeech utterances (clean, 20 and 10 dB SNR, telephone channel) through `StreamAnalyser` at 2–5 frames of look-ahead and compares each frame with the batch track.

- **`Config::lookahead_frames` defaults to 4 (was 5).** It is `min_run_frames − 1`: the frame being emitted plus four more make the 5-frame (50 ms) run the jump guard needs (handbook §3.2, "reject jumps > 7 ST … unless sustained > 50 ms"). So the live trace never draws a short octave jump that batch analysis rejects. Mic→screen on the owner's iPhone should fall from 104 ms to about 94 ms median, under the handbook's ~100 ms budget.
- **Results.** On clean and noisy speech, 4 frames gives a track identical to batch (0 differing frames) and the same accuracy against Praat as 5. Through the telephone channel 0.16% of frames differ, never by an extra F0, only a median neighbour moved by more than 1 ST, and never for more than one frame. 2 frames (D13's earlier recommendation) draws about 19 rejected jumps a minute on clean speech (58 through the telephone channel), each up to 20–30 ms, and adds gross errors against Praat (0.90% vs 0.56% clean).
- **Why not exact equality.** The median filter reads two neighbours on each side, and each neighbour's guard decision needs its own four frames ahead, so exact equality needs `min_run_frames − 1 + radius` = 6 frames (~114 ms). 5 was not exact either. The rare telephone-channel difference costs nothing visible; 6 would miss the budget.
- **Recordings are unaffected.** Stored and scored recordings go through batch analysis, which sees the whole track.
- **Diagnostics.** The FFI exports `live_lookahead_frames()`, the export records it as `settings.lookaheadFrames`, and `harness/validation/device.py` now streams the clip with that look-ahead (5 for older exports) when checking that the phone computes what the core computes, since streamed and batch frames may now differ.
- **Tests.** `default_lookahead_never_draws_a_rejected_octave_jump` (core) streams a 45 ms octave burst: batch and the default live track drop it, 2 frames draws it. `harness/tests/test_lookahead.py` gates the default on clean LibriSpeech: no extra F0 frames, at most 0.2% differing.
- **To confirm on the phone:** the next diagnostics clip should show mic→screen p95 under 100 ms. The p95 estimate is about 98 ms, so there is little margin; if it misses, the next lever is the I/O buffer or the analysis window, not the jump guard.

## D17 · Feedback engine: numbers in Rust, decisions in TypeScript (Stage 3)

- **Utterances are the unit of scoring.** `newvoice-core::utterance` cuts the live frame stream into utterances: a 300 ms unvoiced gap ends one, and 12 s of speech forces a split. It keeps each utterance's audio and measures it with the same batch code that scores recordings: pitch statistics, the F0 slope over the last 300 ms (rising above +2 ST/s, handbook §3.5), median F1–F3 over frames with confidence ≥ 0.5, CPPS, HNR, jitter, shimmer, H1*–H2* and alpha. It also adds the resonance score and weight index when the exercise's vowel and the user's weight baseline are known. Utterance scores are shown only when at least 1 s is voiced (handbook §3.1). `UTTERANCE_VERSION` 1.
- **On the phone**, `LiveAnalyser` runs the segmenter beside the stream analyser. `pull_utterances()` measures finished utterances outside the analyser's lock, and the iOS module calls it on a utility-priority queue about every 250 ms and on stop, then sends each summary as an `onUtterance` event. A 3 s utterance costs about 0.35 s at 48 kHz on x86, off the live thread. The analyser holds at most 8 unmeasured utterances. `set_feedback_context(vowel, weight_baseline)` also adds per-frame `resonance` and `weight_index`. `newvoice-cli utterances` reproduces the phone's summaries from a WAV.
- **Decisions and presentation are pure TypeScript** in `app/src/feedback/`, with no React Native imports, so `npm test` runs them under Node. Siblings import each other with `.ts` paths (`allowImportingTsExtensions`). The Release `.ipa` build (iOS build run 18) bundles them, so Metro accepts these paths.
- **Zones** (`zones.ts`):
  - Targets step from the baseline by +1 ST or +3% F2 per mastered level (§3.9).
  - The pitch zone is ±2 ST around its centre, since §2.6 calls an F0 SD under ~2 ST monotone. The F2 zone is ±3%.
  - Goal ceilings:
    - *feminine / flexible:* 200 Hz (Sumian's training pitch, §1.2) and the higher reference group's F2 mean;
    - *androgynous:* ~159 Hz, the geometric centre of the 145–175 Hz ambiguous zone, and the geometric midpoint of the reference F2s;
    - *own:* baseline steps only.
  - **The zone never reaches above the comfortable p90.** F0 above it is classed `above-comfortable`, drawn in the caution colour and never rewarded (§2.4, §3.9). Zones never pull a voice below its baseline.
  - In-zone success is 70% of voiced frames (E14).
  - Until Stage 5 skill state exists, the practice screen has a manual target-step stepper.
- **Readouts** (`readout.ts`) use rolling medians. Formant readouts hide below 0.5 confidence and are dimmed from 0.5 to 0.7.
- **Feedback fading** (`fading.ts`): each view runs as *live*, *summary* (no trace, a card per utterance) or *delayed* (each utterance's trace is replayed after it ends) (§2.5).
- **Views** (`app/src/feedback/views/`, Skia):
  - pitch trace with the target band and a dashed comfortable-p90 line;
  - pitch × resonance map;
  - F1×F2 vowel chart with 1- and 2-SD reference ellipses from `referenceNorms.ts`, which `harness/norms/build_norms.py` now generates and `--check` covers;
  - summary card (knowledge of results plus a "why" line);
  - rest prompt with a 0–10 effort self-report.
- **Practice screen** (`/practice`, linked from home): optional vowel, mode switch, the views, and the strain monitor. Without a stored baseline it offers *Use this session as my starting point*, a **provisional baseline**. It needs 10 s of scored speech, takes the speaking p10/p90 as a conservative comfortable range until Stage 4's glide, and is stored as a `baseline.provisional` recording and `user.baselineId`.
- **The weight index is not shown yet.** The `Baseline` has no weight baseline until Stage 4's baseline capture stores `measure_voice_quality`'s `weight_baseline`, so `weightIndex` stays null in practice.
- **Deferred: the LPC "wave" view.** The plan lists it as optional. It would need the per-frame spectral envelope sent across the bridge at 100 frames/s, and the F2 readout and vowel chart already give the TruVox-style resonance feedback. Revisit with the Stage 5 resonance lessons.

## D18 · Strain monitor rules and their evidence (Stage 3)

Evidence: [`validation/stage3-strain.md`](validation/stage3-strain.md), generated by `harness/validation/strain.py --report`.

- **Rules** (`app/src/feedback/strain.ts`, `STRAIN_RULES`). Any one asks for a rest (handbook §2.4):
  - jitter rising ×2.0 and by ≥ 0.5 points;
  - shimmer rising ×1.8 and by ≥ 3 points;
  - CPPS falling ≥ 5 dB;
  - a scored utterance's median F0 above the comfortable p90 (immediately);
  - effort ≥ 6/10.
- **How trends are compared:** the median of the last 3 scored utterances against the first 3 of the session (or since the last rest), once 6 are in. Each acoustic sign is raised once per rest period. While the prompt shows, the microphone stops. Acknowledging the rest resets the trend reference.
- **Calibration.** Thresholds sit above the largest change any healthy session showed, and below what deliberately strained sessions reach.
  - Healthy maxima: jitter ×1.82, shimmer ×1.54, CPPS −3.68 dB. These come from 40 LibriSpeech dev-clean speakers (their first 10 read utterances, 626 scored utterances) and 4 healthy synthetic sessions (steady, alternating loudness, a 1.5 ST rise inside the comfortable range).
  - Result: **all 8 deliberately strained sessions get a rest prompt** (jitter, shimmer, aspiration noise, combined, F0 above p90; at utterance 5–10, always after the onset), and **none of the 44 healthy ones do**.
- **Limits.**
  - The strained voices are synthetic (per-cycle jitter and shimmer, aspiration noise). No recordings of strained trans voices exist to test on, and asking anyone to strain on purpose would contradict the safety rules.
  - Trend rules need six scored utterances, so the opening minute of a session is covered by the F0 and effort rules only.
  - The jitter and shimmer margins over healthy read speech are small (about 10% and 17%). Practice on fixed material should vary less than read speech, but revisit with real practice data.
- **CI** regenerates the synthetic sessions and fails if the fixture is stale (`validation.strain --check`). The LibriSpeech sessions need the 338 MB tarball, so they are regenerated locally (`--real`); only derived numbers are committed (LibriSpeech is CC BY 4.0, credited in `NOTICE`).

## D20 · Baseline capture (Stage 4, second iteration)

The handbook's baseline (§4.3; Unit 0 in §4.1): sustained /a/ /i/ /u/, a glide, a reading passage and 30 s of spontaneous speech. Onboarding now hands over to it, it can be put off ("Not now"), and Home offers it until one is stored, then offers to record it again.

- **Measured on the phone by the Rust core's recording path, not the live analyser.** Each task records with the existing test-clip machinery (`start({ recordSeconds })`), then `analyseLastClip({ kind })` runs `analyse_recording` and `measure_voice_quality` with pYIN (D11's recording default) and, for vowels, `measure_sustained_vowel`. It runs on a background queue in Swift (`TaskAnalysis.swift`). The clip is dropped from memory before analysis starts, so audio is analysed once. Only the computed values reach JavaScript; audio never does.
- **Audio is kept only when the user chose to keep it** (D15: metrics-only is the default). Native code then writes the WAV to `Documents/recordings/baseline-<id>/<task>.wav` with complete file protection, so it can't be read while the phone is locked. It refuses any path outside `recordings/`. Discarded attempts have their file deleted.
- **What each task gives.** Vowels: steady-state F1–F4, the chosen formant ceiling, ΔF/aVTL and formant confidence. Glide: pitch percentiles. Reading and spontaneous speech: pitch statistics, voice quality and the weight-index baseline. Every recording also stores whether iOS honoured measurement mode, Bluetooth input, the iOS mic mode, dropped samples, clipping and the median level of voiced frames. Levels are relative only (handbook §3.1).
- **The core now reports the 5th and 95th F0 percentiles** (`PitchStats::p5_st`, `p95_st`; also in the FFI and `newvoice-cli` output). The comfortable range is the glide's 5th–95th percentile (handbook E2). It already reported their difference.
- **The stored summary** (`BaselineSummary`, version 1, in `app/src/baseline/plan.ts`):
  - **Everyday speaking pitch** comes from spontaneous speech, falling back to the reading. The handbook notes that conversation generalises better than passages (E16).
  - **Comfortable range** is the glide's p5–p95. Its **ceiling is the glide's p90**: the handbook's "never reward F0 above the user's comfortable 90th percentile" (§2.4, §3.9). Stage 3's strain monitor and Stage 5's exercises read it from here.
  - **The resonance score** is computed over the three vowels, each weighted by its formant confidence (D11).
  - **The formant ceiling** is the median of the three vowels' chosen ceilings, for use in live analysis. **ΔF/aVTL** is the median over the vowels, since one vowel's ΔF is noisy.
  - **The weight-index baseline** comes from the reading, which has fixed phonetic content, falling back to spontaneous speech. The handbook's weight index is "relative to the user's baseline" and names no task (§3.4).
  - **Voice quality** is stored for the sustained /a/ and for the reading, for strain trends later.
- **Checks on each recording.** A failed check means the recording isn't usable and must be done again. A warning lets the user keep it or try again.
  - Fails: less voiced audio than the task needs. The handbook asks for at least 1–2 s (§3.1); vowels need 1.5 s of a 4 s hold, the glide and reading 2 s, spontaneous speech 5 s. More than 0.1% of samples at full scale (clipping). For vowels, no steady vowel found. For spontaneous speech, stopping before 20 s.
  - Warns: formant confidence under 0.5, the point where F1/F2 are as likely wrong as right (D11). A glide narrower than 4 ST; the message never asks the user to push further (E2: "never push range in one session"). Bluetooth input, a non-standard iOS mic mode, a session that wasn't in measurement mode, or dropped samples.
  - The 4 ST and 0.1% figures are heuristics, not handbook values. They need checking against real baselines.
- **No live pitch while recording,** only a level meter and a countdown. The baseline should capture the everyday voice, not one steered by a readout.
- **Results use neutral words** (D2). The summary shows speaking pitch (Hz and nearest note), the comfortable range and where its ceiling sits, and per-vowel formants. The resonance score is stored but not shown as a number, so a 0–1 position between two reference groups isn't read as a gender score. There's no pass/fail.
- **Reading text: six CAPE-V sentences** (handbook E16). They are short, freely used for voice assessment, and each stresses different sounds.
- **Storage.** A new `baseline` table (migration `0002_baseline`): `completed_at`, `summary` JSON, `session_id` and `analysis_version`. `recording.baseline_id` ties each task recording to its baseline and is deleted with it. `user.baseline_id` points at the current completed baseline. Earlier baselines are kept for later progress comparisons. Starting a new baseline deletes any unfinished one, with its recordings and audio. A baseline also creates a `session` row with its duration.
- **Feeding Stage 3 (supersedes D17's provisional-baseline storage).** `user.baseline_id` now always names a `baseline` row.
  - `feedbackBaselineFrom()` turns the stored summary into the feedback engine's `Baseline`:
    - speaking median and p10/p90;
    - the glide's p10 and p90 as `comfortableP10St`/`comfortableP90St` (the p90 is the safety ceiling the zones and strain monitor use);
    - F2 by vowel code for vowels measured with confidence ≥ 0.5;
    - the resonance score.
  - The practice screen reads the captured baseline this way.
  - *Use this session as my starting point* now saves its provisional baseline as a completed `baseline` row. Migration `0002` moves an existing `baseline.provisional` recording there too.
  - Home treats a provisional baseline as a stand-in and still offers the full recording.
- **The weight baseline is stored but not yet passed to live practice.** `StartOptions.weightBaseline` would turn on weight-index readouts, which D17 left unshown. That is a separate Stage 3 view change.
- **Tests.** `app/src/baseline/plan.test.ts` covers:
  - the task list against the handbook;
  - every check;
  - the summary: range from p5/p95 and ceiling from p90, the speaking-pitch fallback, ceiling and ΔF medians, resonance tokens and weights, the reduced-accuracy flag.
  - The core test for `PitchStats` checks p5/p95 against the reported range.
- **Not tested on a phone yet.** The Swift side can't be compiled in the Linux dev container; the iOS workflow builds it.

## D21 · Curriculum engine, content and ear training (Stage 5; Units 7–10 for Stage 7)

- **The curriculum is data.** `content/curriculum/curriculum.json` (schema version 1) holds Units 0–10 → lessons → exercises, plus the shared warm-up and cool-down. Metro bundles it from `../content` (`watchFolders`), so EAS Update can change it without an app release. `app/src/curriculum/validate.ts` checks it in CI (`curriculum.test.ts`) and again when the app loads it; the app refuses a file that fails. The checks: unique ids; both tracks list every unit and start with Setup; a warm-up of at least 3 minutes and a cool-down of at least 1; one checkpoint lesson per unit, last, holding the unit's gate; every gate has a machine-checkable criterion and is never a loud exercise; each criterion is one its exercise type can measure; brightness zones name a vowel the norms know; whisper and melody criteria have a reference exercise earlier in the unit; pitch-match targets stay within 4 ST of the zone centre; and the copy has no gendered or clinical words (D2, D3).
- **Exercise types** (one renderer each in `app/src/lesson/exercises.tsx`): info, SOVT steps (E11), listen (§2.3), match-pitch (E1), glide (E2, E4, E5), hold (E3, E9, E14), whisper (E6, E7), vowel ladder (E9), read (E10, E15, E16, E19), free speech (Unit 9), self-rate (§4.1 "self-rating vs metrics"), mission (Unit 10) and journal.
- **Unit gates are the handbook's unlock criteria (§4.1)**, implemented in `app/src/curriculum/criteria.ts`. Where the handbook left a choice, this is how it was read:
  - *Unit 1:* a fixed 10-trial block at staircase level 4 (1 ST, 8% formant shift, 5 dB H1–H2), ≥ 80% correct. "≥ 80% on staircase at set difficulty" can't be met inside an adaptive run, which hovers at 79%.
  - *Unit 2:* E1's check: a window of ≥ 600 ms whose median F0 is within ±50 cents of the target, on 8 of 10 notes. Voiced runs bridge gaps of up to 30 ms, as the jitter tracker does (D10). Targets are offsets around the current pitch-zone centre, capped 0.5 ST under the comfortable p90.
  - *Unit 3:* "weight index ≥ baseline + 0.5 SD over 3 sessions" is read as *lighter* by 0.5 SD: the median weight index of scored utterances ≤ −0.5 (positive is heavier, D10), in three separate sessions, with no utterance above the comfortable p90.
  - *Unit 4:* "whispered F2 +8% vs baseline". The baseline has no whisper, so Unit 4's first lesson records the user's ordinary whisper as the reference; the checkpoint compares against the latest one. A reading needs 0.5 s of frames with formants at confidence ≥ 0.5 (whispered frames get exactly 0.5, D11).
  - *Unit 5:* resonance score ≥ 0.5 on 6 of 7 vowels (/i ɪ e ɛ æ ɑ ʌ/), capped at the goal's position (0.5 for androgynous). The "own" goal has no reference position, so its target is the baseline score + 0.15, capped at 0.5.
  - *Unit 6:* ≥ 70% of voiced frames in both the pitch and the F2 zone on a 20-word /i/ list. Because the words share a vowel, the F2 zone applies. Frames with formant confidence under 0.5 are left out of the F2 share rather than failed.
  - *Unit 7:* E15's "+3 ST over baseline". The baseline's reading range is over a whole passage and isn't comparable with per-phrase ranges, so Unit 7's first lesson records an everyday reading of the same kind of lines as the reference. The median phrase range must be ≥ the reference + 3 ST, and ≥ 50% of questions must end rising (> +2 ST/s, §3.5).
  - *Unit 8:* "self-rated + metrics": mean self-rating ≥ 6/10 and ≥ 50% of voiced frames in the pitch zone. The /s/ centre of gravity (Stage 7 plan) is not measured: it needs ≥ 22.05 kHz with no roll-off, which the phone path doesn't guarantee yet.
  - *Unit 9:* "stable metrics in free speech": a 60 s talk passes when its median F0 is in the pitch zone, and the gate needs three sessions whose medians are within 2.5 ST of each other. On 40 LibriSpeech readers split into three ~15 s sessions (the strain fixture, D18), 2.5 ST holds for 33 of 40; the 1.5 ST first tried held for only 25 (`stability.test.ts`). Resonance isn't scored in free speech (no alignment in v1).
  - *Unit 10:* self-reported missions.
- **Progression.** Units open in track order when the previous unit's gate is met; lessons in a unit open one after another; a lesson is done when each of its exercises has met its criterion. The resonance-first track runs 0, 1, 4, 5, 2, 3, 6–10 (§2.1).
- **Quiet mode** skips exercises marked `loud`; the validator stops a loud exercise from being a gate, so quiet mode never blocks a unit. Onboarding's "quiet only" environment turns quiet mode on.
- **Not included:** E13 soft onsets (no validated attack-time measure on the phone yet), E17 shadowing (needs consented, licensed voices) and E18 negative practice (the handbook warns it can be hard for dysphoric users). The LPC "wave" view stays deferred (D17).
- **Ear-training stimuli are synthesised on the phone** (`app/src/eartraining/synth.ts`): a harmonic source (−6 dB/octave) through a five-formant Klatt cascade. F1–F3 sit midway between the Hillenbrand groups for the vowel (/ɑ æ ɛ ɪ/, roving), F4 and F5 at 1.3 and 1.6 × F3. Without an F5, LPC put its spare pole between F1 and F2. Base F0 roves over 130–220 Hz. Pitch pairs differ in F0 only, brightness pairs in a formant scale factor only, weight pairs in H1–H2 only (H1 +0.8Δ, slope −0.2Δ dB/octave, so H1–H2 changes by exactly Δ). Each sound is normalised to the same RMS.
  - `harness/tests/test_eartraining.py` renders pairs at the easiest, checkpoint and finest levels and measures them: Praat F0 shows the asked semitones (within 1%) and no F0 change elsewhere; the spectrum shows the asked H1–H2 change on weight pairs, and on other pairs only the change the formant envelope predicts (an independent Python resonator). Praat formants (wide poles dropped, D8), on the same pair re-rendered at 100 Hz F0 where LPC is reliable, are within 8% of the targets, and brightness pairs differ by the asked ratio within 2%.
  - Synthesis rather than shipped recordings: any difference size the staircase asks for, nothing to license, and nothing to download. **Pending:** natural-voice stimuli (for example LibriSpeech through Praat's "Change gender", CC BY 4.0) once synthetic items have been tried.
- **Staircase:** 3-down/1-up, which converges on 79.4% correct (Levitt 1971), the handbook's ~80%. Ten levels per dimension: pitch 4 → 0.15 ST, brightness 20 → 2% (spanning §2.3's 5–20%), weight 12 → 1 dB.
- **Playback** uses `expo-audio` (SDK 58), with background playback and background recording off in its config plugin. Stimuli are written to the cache folder and played; recorded audio is never played here.
- **Still pending (D4):** the content licence. The curriculum is Apache-2.0 with the rest of the repository until the owner decides; CC BY-SA 4.0 is the recommended alternative.

## D22 · Learning loop: refreshers, feedback fading, motivation (Stage 6)

All pure TypeScript in `app/src/learning/`, tested by `learning.test.ts`, which includes an 8-week simulation (the Stage 6 exit).

- **Skills.** Each lesson is a skill for refreshers and mastery (`skill_state` row `lesson:<id>`); each unit holds the target level (`unit:<id>`).
- **Refreshers: half-life regression adapted to motor skills** (`hlr.ts`). p = 2^(−Δ/h), h = 2^(θ·x), x = (1, √(1+successes), √(1+failures)), as in Settles & Meeder (2016). Recall is replaced by measured performance: a refresher's `Outcome.performance` (0–1, how much of the criterion was met). θ is learned per skill on the phone with the paper's loss, changed in two ways for single online updates:
  - the half-life term is (log₂ h − log₂ ĥ)²; with the paper's (h − ĥ)² a run of good refreshers overshot and collapsed h to its floor;
  - the regulariser pulls θ toward the starting weights (−1, 1, −0.5), not toward zero. Those weights give about a day after the first success, ~3 days after 9 and ~12 after 25.
  - α 0.1, λ 0.01, learning rate 0.05; h is clamped to 6 hours–120 days. A refresher is due when predicted performance falls to 0.5. In the simulation a learner who keeps a skill reaches h ≈ 68 days and one who loses it settles near 3.
  - Written from the paper's equations, not Duolingo's code, so there's no MIT notice to carry (D5).
- **Mastery** moves halfway to each run's performance, after decaying by the predicted retention since the last success (§4.2).
- **Feedback fading (§2.5).** Below mastery 0.4 every item gets live feedback; from 0.4 to 0.75, alternate items (50%); from 0.75, summary only. The why-line (knowledge of performance) shows below mastery 0.5, and always on checkpoints and failed attempts; above that, results only.
- **Practice order:** authored (blocked) until a lesson has been passed once, random afterwards and in refreshers (§2.5).
- **Challenge point:** over the unit's last 5 scored attempts, more than 80% passed steps the target level up (zones.ts: +1 ST or +3% F2), under 70% steps it down. Zones still stop at the comfortable p90, so a higher level never asks for more than is comfortable.
- **Session plan** (`plan.ts`): the most overdue refreshers (at most 2), then the next lesson, if they fit in what is left of the 20-minute soft cap and the hour a day, minus 4 minutes for the warm-up and cool-down.
- **Motivation with guardrails** (`motivation.ts`):
  - XP: 2 per voiced minute up to 40 a day (20 minutes), 0.5 per listening answer up to 15, 5 per lesson up to 15. Practising past one session's worth earns nothing more.
  - Streaks: any practice counts a day, listening included. Up to 2 missed days per trailing week are credited as rest. Days marked as voice rest or illness, and hard-stop days, keep a streak alive without adding to it. Today never breaks it.
  - No hearts or lives anywhere.
  - The home screen celebrates process (consistency, minutes, a wider comfortable range), never outcomes.

## D23 · Safety layer and the rest of Stage 4

- **Safety limits** (`app/src/safety/rules.ts`, constants, no setting changes them; D2):

  - 1-minute cool-down;

  - 60-minute daily maximum, which blocks even a new warm-up but never the cool-down.

Listening, reading and the journal stay open.

- **Quick-exit gesture: shake.** Three jolts over 2.5 g within 1.2 s, each at least 120 ms apart (`app/src/privacy/shake.ts`; walking and setting the phone down don't trigger it). On by default, with a setting. It listens only while the app is unlocked and showing.
- **Discreet icon (iOS):** two neutral alternate icons (dots, waves) generated into the asset catalog by `plugins/withAlternateIcons.js` and set through a small local module, `modules/newvoice-discreet`. iOS can't change an app's name at runtime.

  - **Pending:** Android (activity aliases).
  - Store rules: alternate icons must not imitate other apps, which these don't.
- **Developer tools (settles D13's pending decision).** The capture test and diagnostics export are behind Settings → Developer tools, off by default. The route redirects home without it.
- **Whisper mode** hides pitch on the free-practice screen. **Quiet mode** skips loud exercises (D21).
